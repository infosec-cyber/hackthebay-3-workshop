Part 1
The Mindset

this part is short. on purpose.

You already do this

Ever debugged code that should work?

Stared at it until you noticed the one assumption that was wrong?

That's hacking.
Same skill. Different target. Their assumptions instead of yours.

Important reframe for developers in the room. You're not learning a new skill. Debugging is: "the program is doing something I don't expect, find out why." Hacking is: "make the program do something THEY don't expect." Same muscle.

You are not a pentester

You are a very confused user

The app expects you to click "Submit".
You click "Submit" and then ask: what did that actually send?

Methodology comes later. Scanners come later. Step one is just... watching. Using the app with DevTools open. Being nosy.

Three questions. Tattoo them.

  1. Where does my input go?
  2. What does the server trust that it shouldn't?
  3. What happens if I lie?

Every OWASP category is one of these three, wearing a costume.

I'm going to keep coming back to these. Every bug in this talk answers one of them. SQL injection = "where does my input go" (into a query). IDOR = "what does it trust" (the ID I sent). Password reset bypass = "what if I lie" (about which account I am).

When you find something weird

You get 15 minutes to chase it.

After 15 minutes: write it down. One line. Move on.

90% of my real bugs came from the "come back later" list.
Weird stays weird. It'll still be there.
The list is everything. Beginners either ignore the weird thing (and lose the bug) or chase it for 3 hours (and lose the day). 15 minutes. Write it down. The Elementor CVE sat on my list for 2 weeks.

Part 2
One Bug, Slowly

Restaurant SaaS platform · Critical · $2,000

Every decision. Every wrong turn. The whole thing.

This is the core of the talk. I'm going to walk through ~20 minutes of actual work, slowed down. The bug is not impressive. The PROCESS is what I want you to take home.

Minute 0: What am I even looking at

Restaurant management dashboard. Orders, menus, payouts.
I have a free trial account. One fake restaurant.
I don't know this app. I don't know what it does. I'm going to click every button and watch the Network tab. Not testing anything yet. Just learning what "normal" looks like.

← This step is where most people skip ahead. Don't.

You can't find "abnormal" if you don't know "normal". I spend the first 20 minutes on ANY target just... using it. Like a customer. DevTools open, Network tab filtered to XHR. Watching.

Minute 5: Something boring catches my eye


GET /api/feature-flags HTTP/1.1

HTTP/1.1 200 OK
{
  "new_menu_editor": true,
  "payouts_v2": false,
  "export_beta": false,
  "bulk_refunds": false,
  ...
}
Feature flags. Some are false. Question #2: what does the server trust? It trusts these flags to hide things from me. But the flags are coming TO me. In my browser.
I'm not excited yet. Feature flags are everywhere. But notice the QUESTION that fired: "what does it trust?" It trusts these booleans to gate features. And it's sending them to a place I control.

Minute 6: Okay so what if I lie

Burp → Proxy → Match and Replace → Response body:


Match:    "enabled": false
Replace:  "enabled": true
I'm not trying to "hack" anything. I just want to see what the UI looks like with everything turned on. Maybe it's all placeholder. Maybe there's nothing there. One way to find out.

Cost of this experiment: 30 seconds. That's why you try it.

This is Question #3: what if I lie? But notice — I'm not lying to the SERVER yet. I'm lying to my own BROWSER. Low risk. Fast. Just seeing what's behind the curtain.

Minute 7: Refresh. New buttons.

Three new things appeared in the UI:

1. A "Bulk Refund" button (looks half-built, form doesn't submit)
2. A new menu editor (works, boring)
3. An "Export" button on the Payouts page
"Export" is a cursed word. Export features are always added late, by a different team, under time pressure. They copy the auth check. They forget the ownership check.
This is pattern recognition from experience — but you can BORROW mine. "Export", "Report", "Download CSV", "Bulk" — these words mean "built fast, tested less." You'll build your own list of cursed words.

Minute 8: I click the button


POST /api/payouts/export HTTP/1.1
Authorization: Bearer eyJ...

HTTP/1.1 200 OK
{
  "download_url": "https://blob.../PAYOUT-bd78d6....csv?X-Amz-Signature=..."
}
It worked. It actually worked. The feature was "hidden" but the API was live. Okay — but this might still be fine. Let me download the CSV and see what's in it before I get excited.
Important: I haven't found a bug yet. The button works — so what? Maybe it exports MY data. That's... a feature. Don't report yet. Look at what you actually got.

Minute 9: Open the CSV


restaurant_id, restaurant_name,    period,   amount,    bank_last4
8812,          Rotem's Test Cafe,  2024-Q4,  $0.00,     ****1234
1003,          Mario's Pizza NYC,  2024-Q4,  $48,203,   ****8821
1005,          Golden Dragon SF,   2024-Q4,  $31,887,   ****4420
1007,          ...
That is not my data. That is everyone's data.

Critical. Report. Done.

NOW it's a bug. The endpoint had auth (you need a valid session) but no FILTER. It dumped the whole table. The developer assumed: "this button is hidden, so only internal people will click it." The button was hidden. The API was not.

The whole thing, compressed

00:00 Open app. DevTools. Click around.
05:00 Notice feature-flag response. Q2: what does it trust?
06:00 Flip all flags to true in my browser. Q3: what if I lie?
07:00 New "Export" button appears. Cursed word.
08:00 Click it. API is live. Get a CSV URL.
09:00 Open CSV. It's everyone's payout data.
09:30 Write report.

Nine minutes. No Burp Intruder. No payloads. No scanner. Just looking, and asking the three questions.

THIS is what I want you to remember. Not the bug — the rhythm. Look → notice → question → cheap experiment → look at result → repeat. The bug falls out of the process. You don't aim at it.

The two lessons

Hidden ≠ Protected

If the gate is in the frontend,
there is no gate.

Feature flags, disabled buttons, commented-out HTML, display:none — all of it is a suggestion.
Try the cheap thing

Flipping flags cost 30 seconds.
If it did nothing: 30 seconds lost.

Beginners overthink. "Is this worth trying?" If it takes under a minute — just try it.

Part 3
Three More, Fast

Different apps. Same three questions.

Now I speed up. Three bugs, ~2 min each. The goal: you start to see the SHAPE repeat. By the third one you should be ahead of me.

Bug 2 · Password reset $3k

Retail chain. SMS OTP flow. Standard stuff.


# Step 1 — I ask for a code to MY phone
POST /forgottenPassword  {"target": "555-0001"}
→ SMS arrives with code 090038

# Step 2 — I submit the code
POST /forgottenpasswordtokens
{ "otpVerify": { "target": "555-0001", "passphrase": "090038" },
  "mobile":    "555-0001" }
Wait. Why is the phone number in there twice? otpVerify.target and mobile. Same value. If they were always the same... you'd only need one.

Bug 2 · What if I lie


POST /forgottenpasswordtokens
{ "otpVerify": { "target": "555-0001", "passphrase": "090038" },
  "mobile":    "555-9999" }     ← victim's number

→ { "token": "eyJ...sub: VICTIM_USER_ID..." }
OTP was checked against otpVerify.target ✅
User to reset was looked up by mobile ✗
Two fields. One validated. Account takeover on anyone.
Same three questions. Q1: where does my input go? Into TWO places. Q2: what does it trust? It trusts both fields to match. Q3: what if I lie? I make them NOT match. The tell was the duplication. Duplication = two code paths. Two code paths = one of them is wrong.

Bug 3 · Follow the weird $20k

Secure messaging app. File download by GUID.


# Normal request
GET /fileproxy?guid=a1b2c3d4-...-f00d
→ 200 OK [file bytes]

# I send a guid with one character changed. Expecting: 404
GET /fileproxy?guid=a1b2c3d4-...-f00e
→ 200 OK <!DOCTYPE html><title>HackerOne</title>...
I asked for a file. It gave me HTML. Of hackerone.com.
My test account email is @wearehackerone.com.
...did it just fetch my email domain?
We weren't looking for this. We were testing something ELSE. Sent a bad GUID expecting an error. Got HTML instead. That is WEIRD. And weird = stop everything, 15 minute timer, chase it.

Bug 3 · Chase it for 15 minutes


# Theory: GUID not found → fallback → fetch email domain as URL
# Test: register new account with email me@my-server.com

GET /fileproxy?guid={invalid}
→ my-server.com gets a hit ✅  theory confirmed

# my-server.com now responds: 302 → http://169.254.169.254/latest/...
GET /fileproxy?guid={invalid}
→ {"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"..."}

Error branch → URL fetch → follows redirects → AWS metadata → prod IAM creds.
The bug was in the code path nobody reviewed.

The happy path had tests. The "GUID not found" branch was a dev shortcut that shipped. $20k. Q1: where does my input go — into a URL fetcher, apparently. Q2: what does it trust — it trusts that GUIDs are always found. Q3 answered itself.

Bug 4 · Read the check AWS Console

Pop DevTools. Sources tab. Ctrl+Shift+F: addEventListener('message'


window.addEventListener('message', (e) => {
  if (/amazon\.com/.test(e.origin)) {
    handle(e.data);
  }
});
Regex. No $ at the end.
/amazon\.com/ matches amazon.com.evil.net. And evilamazon.com.
That's Question #2. It trusts that regex to validate origin. Badly.
This one is different — I didn't poke the app. I READ the app. Searched for the message handler, read the origin check, spotted the missing anchor. Five minutes. The handler only controlled dark mode so small bounty — but this EXACT pattern, with real impact, I've hit a dozen times. When you see an origin check, read it like a regex crossword. Where's the hole?

It's the same bug

Q2: What does it trust?Q3: The lie
ExportFrontend hides the buttonFlip the flags
Password resetTwo fields matchMake them not match
File proxyGUIDs are always validSend a bad one
postMessageRegex validates originDomain that matches anyway

Different tech. Different payloads. Same two questions, every time.

This is the whole talk on one slide. You don't need 100 techniques. You need to ask "what does it trust" and "what if I lie" over and over until something falls over. The techniques are just HOW you lie in a specific context. The questions are the job.

Part 4
Before AI / With AI

What changed. What didn't. How to use it without rotting your brain.

How I used to learn a target ~2019


# Download their main.js. 400KB minified hell.
curl https://target.com/static/main.a8f3c.js -o main.js
js-beautify main.js > readable.js   # 18,000 lines

# Then just... grep. For hours.
grep -n "fetch\|axios\|XMLHttpRequest" readable.js   # find API calls
grep -n "localStorage\|sessionStorage\|cookie" readable.js
grep -n "postMessage\|addEventListener" readable.js
grep -n "eval\|innerHTML\|document.write" readable.js

# Open readable.js at each line number. Read around it.
# Build a map in your head. Where does data flow?

Slow. Painful. Boring. And it built intuition that never left.

This is what it looked like. Hours of grep and reading. And it SUCKED. But — by the time you'd read 18,000 lines of their code, you UNDERSTOOD that app. You knew where the bodies were buried. That understanding is where bugs come from.

What the grind actually gave you

Pattern library in your head

You've read 50 broken origin checks. The 51st, you see it in two seconds. Not because you're smart — because you've seen it.
A feel for "weird"

Noticing the duplicate field. Noticing the fallback branch. That's not a technique. It's miles. You only get it by reading code that wasn't yours.

This is the part I'm worried beginners will skip now.
Don't skip it. Just do it faster.

The "10,000 hours" thing is overblown but there's a core truth: you need REPS. Reading code, poking apps, seeing what broke. AI compresses this — but it doesn't replace it. You still need to build the "huh, that's weird" detector. AI doesn't have one. It has averages.

Now: AI as a thinking partner the good

Paste the minified JS you don't understand:
"Explain what this function does. What inputs does it take? Where do those inputs come from? What would make it misbehave?"

Paste the validation you're staring at:
"This checks a callback URL. List every way a malicious URL could pass this check. Assume I can register any domain."

When you're stuck:
"I can inject into header X of an internal request. I can't see the response. What can I do with a blind header injection?"

It's a rubber duck that knows every RFC.

THIS is the unlock. Not "find bugs for me." It's "help me THINK about this specific piece." It's a senior engineer you can ask dumb questions at 3am. It knows what \u2028 does. It knows IMDSv2 hop limits. It knows every obscure browser quirk. USE that.

My actual prompts, on real bugs

// the OTP bug — I saw the duplicate fields, asked:
"Here's a password reset request with both otpVerify.target and mobile set to the same phone. Why would a backend need both? What goes wrong if I change only one?"

// the postMessage regex — I knew it was wrong, asked:
"This regex validates origin: /amazon\.com/. Give me 10 domains I could register that would match"

// reading a 2000-line bundle, asked:
"Summarize every place this code writes to window.location or innerHTML. For each, trace back where the input comes from."
Notice: I already noticed the weird thing. I already had a hypothesis. The AI helped me EXPAND it, or CONFIRM it faster. It didn't FIND the weird thing. I did. That's still your job.

The trap don't do this


You:  "Here is the source code of an app. Find all the vulnerabilities."

AI:   "Potential issues I noticed:
       1. This endpoint might be vulnerable to SQL injection
       2. This function could have XSS if user input reaches it
       3. Rate limiting may be insufficient
       ..."

Everything "might be" and "could have." It's pattern-matching on what bugs usually look like.
It doesn't know what's weird about THIS app. You do.

AI is trained on average code. It finds average bugs — the ones that look like textbook examples. The real bugs are in the SPECIFIC weirdness of THIS codebase: the fallback branch, the duplicate field, the feature flag. Those don't pattern-match. Those take a human going "huh."

The actual division of labor

Still your jobOutsource to AI
Noticing the weird thingExplaining what minified code does
Asking "what if I lie here?"Listing 20 WAYS to lie
Knowing what's normal for THIS appKnowing what's normal for ALL apps
Deciding what to try nextWriting the PoC once you know what works
Reading the response and going "huh"Decoding the response format

Left column is intuition. Right column is knowledge.
AI has infinite knowledge and zero intuition. You're the opposite. Good trade.

This is the frame I want you to leave with. You bring curiosity and context. AI brings encyclopedic knowledge and infinite patience. Neither of you finds the bug alone. Together you find it in 9 minutes instead of 2 hours.

A beginner loop that works now

1. Use the app. DevTools open. (you)
2. Something looks off. Screenshot it. (you)
3. "Explain what this code does" → paste it (AI)
4. "What could go wrong here?" (AI)
5. Pick the suggestion that matches YOUR weird feeling (you)
6. Try it. Look at the result. (you)
7. "I got this response, what does it mean?" (AI)
8. Repeat from 2.

Same loop as before. Just the slow parts are faster.

This is literally the 9-minute restaurant-SaaS bug, but at step 3 you could've asked "what is a feature flag response used for" and gotten to the flag-flip idea in 30 seconds instead of 2 minutes. Small speedup. But over a day, over a career — compound interest.

The whole talk in one box

1. Watch the app until you know what normal looks like.
2. Ask: where does my input go · what does it trust · what if I lie.
3. Try the cheap thing. Under 60 seconds? Just try it.
4. Weird response → 15 minutes → write it down.
5. Stuck on the HOW? Ask AI. Stuck on the WHAT? That's you.
